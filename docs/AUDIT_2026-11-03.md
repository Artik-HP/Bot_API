### Как трактовать зависимости

В старом коде не обнаружен прямой пользовательский выбор произвольного hostname в callTelegram или callPeerBot: base URL задаётся владельцем, peer выбирается из конфигурации, метод проверяется regex. Поэтому наличие SSRF-advisory в request само по себе не доказывает SSRF всего шлюза.

Для proxy-addr не была подтверждена используемая приложением граница доверия на IP. Для form-data не был доказан доступный пользовательский путь к проблемному multipart-поведению. Парсинг JSON происходил до авторизации, поэтому предупреждения body-parser требуют внимания, но эксплуатация не проверялась. Рекомендация — контролируемое обновление/замена transport с регрессионными тестами, не слепой `npm audit fix --force`.

## Что в шаблоне было удачным

- API-ключ сравнивался через timingSafeEqual с проверкой длины.
- Входные имена методов, peer-имена и числовые настройки валидировались.
- Peer URL определялись конфигурацией, credentials в URL запрещались.
- Для аудио был потоковый контроль предельного объёма, а не доверие только metadata.
- Ошибки большинства HTTP-маршрутов имели единый JSON-формат.
- Были polling/webhook/off и разделение HTTP/TLS на приложение и reverse proxy.

Это полезные заготовки, но сами по себе не формируют отдельный сильный портфолио-продукт.
